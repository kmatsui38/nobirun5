# 技術スタック選定

- 作成日: 2026-08-27
- ステータス: 提案（v0.1 / レビュー待ち）
- 前提: [MVP機能要件 v1.0](01_MVP機能要件.md)、[問題テンプレート設計 v1.0](02_問題テンプレート設計.md)

## 1. 選定の条件

1. **コストを最小化する**（MVPは被験者2名。月額ほぼ0円が理想）
2. **トランザクション増加時に拡張できる**（eスピ！展開で数百〜数千ユーザーを想定）
3. スマホブラウザ最優先のWebアプリ。将来PWA化してプッシュ通知
4. データモデルは**明確にリレーショナル**（機能要件のデータ設計参照: mastery の期日クエリ、解答履歴の集計、将来のコーチ向けレポート・順位集計）
5. 検証のため**解答履歴を自由に集計・エクスポート**できること
6. 少人数開発（AI支援前提）。運用の手間は最小に

## 2. 候補の比較

| 観点 | A. Firebase | B. Supabase + Next.js（推奨） | C. Cloudflare Pages/Workers + D1 |
|---|---|---|---|
| DB | Firestore（NoSQL） | **PostgreSQL**（SQL） | D1（SQLite互換） |
| MVP時のコスト | 0円（Sparkプラン） | 0円（Freeプラン） | 0円 |
| 数千ユーザー時 | 従量課金（読み書き回数依存） | Pro $25/月 + ホスティング | ほぼ無料〜数ドル |
| 期日クエリ・集計 | 苦手（JOINなし、集計は自前実装） | **得意（SQLそのもの）** | 得意（SQL） |
| 解答履歴の分析 | エクスポートに一手間 | **SQL/CSVで自在** | SQLで可能 |
| 認証 | ◎ Firebase Auth | ◎ Supabase Auth | 自前（Auth.js等） |
| プッシュ通知（将来PWA） | ◎ FCM | ○ Web Push(VAPID)で可 | ○ Web Push(VAPID)で可 |
| ロックイン | 強い（Firestoreは移行困難） | **弱い（Postgresはどこへでも移行可）** | 中 |
| 成熟度・開発体験 | 高い | 高い | D1がやや発展途上 |

## 3. 推奨構成: B. Supabase + Next.js

```
フロント+API: Next.js (TypeScript, App Router) — Vercel にデプロイ
DB+認証:      Supabase (PostgreSQL + Supabase Auth)
数式表示:      KaTeX
テンプレート:  リポジトリのYAMLが正 → ビルド/デプロイ時にDBへ同期
```

### Firebaseではなくこちらを推す理由

1. **データモデルがSQL向き**。「今日出題すべき事項（due_date <= today を苦手順に7件）」「単元ごとの定着度平均」「コーチ向けの進捗集計」「受講者間の順位」— すべて素直なSQL。FirestoreだとJOIN・集計がないため、非正規化した集計値を書き込み時に自前メンテすることになり、拡張のたびに設計負債が増える。
2. **検証フェーズの分析が楽**。解答履歴をSQLで直接集計・CSV出力できる（n=2の定性検証でも「どの単元で詰まったか」をすぐ見たい）。
3. **ロックインが弱い**。中身はただのPostgres。eスピ！側のインフラに寄せる必要が出ても、RDS/Cloud SQL/自前サーバへそのまま移行できる。Firestoreからの移行は書き直しに近い。
4. **コストの予測が立てやすい**。無料枠（DB 500MB・認証 月間5万ユーザー）でMVPは余裕。次の段階も Pro $25/月 の固定費で数千ユーザーまで見通せる。Firestoreの従量課金（読み書き回数）は、間隔反復のような細かい読み書きが多いアプリだと膨らみ方が読みにくい。
5. Firebaseの強み（FCM・リアルタイム同期・ネイティブアプリ連携）は**本アプリでは当面使わない**。将来のPWAプッシュ通知は Web Push(VAPID) で実現でき、必要になった時点でFCMだけ部分採用することも可能。

### Firebaseを選ぶ方が良いケース（判断材料）

- **eスピ！が既にFirebase/GCPで動いている**場合（連携・運用ノウハウの共有を優先すべき）
- 将来ネイティブアプリ化を最優先にする場合

→ **要確認: eスピ！の技術スタック**。GCP系ならFirebase選択にも合理性がある。

## 4. コスト見積もり

将来構想の上限は **生徒300名** （2026-08-27 ユーザー確認）。この規模での負荷試算:

| 項目 | 試算 | 各サービスの枠 |
|---|---|---|
| 解答数 | 300人 × 7問/日 = 2,100問/日 ≒ 6.3万問/月 | DBの書き込みとしては軽微 |
| APIリクエスト | 1人1セッション30回程度 × 300人 ≒ 27万回/月 | Vercel Pro の含有枠（100万回超）に余裕 |
| 転送量 | 2MB/セッション × 300人 × 30日 ≒ 18GB/月 | Vercel Pro 1TB / Supabase Pro 250GB に余裕 |
| DB容量 | 出題履歴を全文保存しても 60〜70MB/月、年間 約0.8GB | Supabase Pro 8GB → 数年分。古い履歴のアーカイブでさらに延命可 |
| 認証 | 300 MAU | Free枠(5万MAU)ですら余裕 |

### フェーズ別の月額

| フェーズ | 構成 | 月額 |
|---|---|---|
| MVP（被験者2名） | Vercel Hobby + Supabase Free | **0円** |
| eスピ！展開・上限300名 | Vercel Pro $20 + Supabase Pro $25 | **約7,000円（生徒1人あたり約23円）** |
| 同・最安構成 | Cloudflare Pages（無料・商用可） + Supabase Pro $25 | 約3,800円 |

- **300名は本構成にとって余裕のある規模**。コンピュート増強・アーキテクチャ変更は不要で、Proプランの固定費のみで賄える。
- 販売時はSupabase Pro（日次バックアップ付き）を必須とする。**学習履歴の消失は商品価値の毀損に直結する**ため、Freeプランでの商用運用はしない。
- 注: Vercel Hobbyは非商用利用の規約。**MVP（家庭内検証・無料提供）は問題ないが、eスピ！での販売開始時にProへ移行する**（上表に織り込み済み）。
- 参考: Firebaseでも300名規模なら同様に低コスト（無料枠内〜数百円/月）に収まる見込み。この規模ではコスト差は決め手にならず、選定理由は第3節のデータモデル適合性・分析容易性・ロックイン回避が主となる。

## 5. 開発着手時の初期構成（案）

- リポジトリ構成: 本リポジトリにアプリを追加（`app/` ディレクトリ or モノレポ構成）
- `templates` テーブルへのYAML同期スクリプト（`tools/validate_templates.py` の検証を通過した approved のみ）
- 出題ロジック（セット生成・習熟ボックス更新）は**サーバ側（Next.js API / Server Actions）**に実装し、クライアントには答えを渡す（機能要件どおり採点は即時・ローカル判定でよいが、履歴保存はサーバ経由）
- Supabase Row Level Security で「本人のデータのみ読める」を担保
