## 1. 方式のおさらい（企画書v0.3で決定済み）

- 問題は**型（テンプレート）を統一し、変数だけを動的に差し替える**方式。
- 品質チェックは**テンプレート単位**: AIレビュー + 正式ローンチまでに人の目で全テンプレートをチェック。
- テンプレートごとに**変数の制約条件**を定義する（解の綺麗さ・難易度の統制）。

## 2. テンプレートのデータ形式

テンプレートはYAMLで記述し、`data/templates/` に単元別に配置する。形式は2種類:

- `numeric` — 数値入力（整数・分数）。解答欄は1つ以上の名前付きフィールド（例: x と y）
- `choice` — 選択式（4択目安）。証明の穴埋めなど自動採点できない事項はこちらに変換

### スキーマ

```yaml
id: T-M1-A1-001            # T-<単元ID>-<連番>
item: M1-A1                # 単元ID（math-units.yaml準拠）
item_kind: knowledge       # knowledge | thinking
item_index: 2              # 単元内の事項番号（1始まり）
format: numeric            # numeric | choice
difficulty: 1              # 1=基本 2=標準 3=応用
title: 正負の数の加法

variables:                 # 変数定義（乱択の範囲）
  a: { type: int, min: -9, max: 9, exclude: [0] }
  b: { type: int, min: -9, max: 9, exclude: [0] }

constraints:               # 変数が満たすべき条件（全て真になるまで再抽選）
  - "a + b != 0"

derived:                   # 本文・解説で使う計算値
  ans: "a + b"

body: "次の計算をしなさい。\n{a} + ({b})"

answers:                   # numeric のみ。フィールド名: 正解の式
  答え: "ans"

# choice の場合は answers の代わりに:
# correct: "正解の選択肢（式または文字列）"
# distractors: ["誤答1", "誤答2", "誤答3"]   # 式または文字列。重複・正解一致は検証で排除

explanation: |
  同符号の2数の和は、絶対値の和に共通の符号を付けます。
  異符号の2数の和は、絶対値の差に絶対値の大きい方の符号を付けます。
  {a} + ({b}) = {ans}

status: draft              # draft → ai_reviewed → approved（approvedのみ出題可）
```

### ルール

- **出題の再現性**: 出題時は `テンプレートID + 乱数種(seed)` で変数を確定する。同じseedなら必ず同じ問題になる（機能要件のデータ設計と対応）。
- **変数制約**: `constraints` はテンプレート作成時に必ず定義する。「解が整数になる」「途中式で未習の数が出ない」「難易度が事項の想定を逸脱しない」を式で表現する。
- **再出題時は変数を変える**: 同一ユーザーへの再出題では前回と異なるseedを使う。
- **式の記法**: `variables`・`constraints`・`derived`・`answers` の式は四則演算・比較・整数演算のみ（検証スクリプトが安全に評価できる範囲）。

## 3. 必要本数の算定

単元マスタ（中1+中2 = 15単元）の学習事項数:

| | 知識及び技能 | 思考力・判断力・表現力 | 計 |
|---|---|---|---|
| 中1（8単元） | 20 | 14 | 34 |
| 中2（7単元） | 18 | 12 | 30 |
| **計** | **38** | **26** | **64** |

### 目標本数

| フェーズ | 方針 | 本数 |
|---|---|---|
| 第1弾（検証開始に必要） | 被験者の既習範囲のみ。知識技能の事項に各2本（難易度1・2）、思考力の事項に各1本 | 既習範囲による（全範囲なら 38×2+26×1 = **102本**） |
| 第2弾（ローンチまで） | 全事項に難易度3を追加、手薄な事項を補強 | +64本 目安 |

- 1日5問 × 週7日 = 週35問。同一テンプレートでも変数が変わるため、**第1弾の約100本で出題の回転には十分**（間隔反復は同一事項の再出題が前提のため）。
- 枯渇よりも品質を優先し、本数は「事項のカバレッジ100%」を第一目標とする。

## 4. 制作・検品フロー

```
① AI生成（Claude等でテンプレート下書き）        → status: draft
② 機械検証（tools/validate_templates.py）
   - スキーマ・式の妥当性、制約の充足可能性
   - サンプル100問を実生成し、解の妥当性・選択肢の重複を検査
③ AIレビュー（別プロンプトで数学的正しさ・難易度・解説の質を批評）
                                              → status: ai_reviewed
④ 人の検品（テンプレート単位で数問を実際に解いて確認）
                                              → status: approved（出題可）
```

検品を助けるツール:

- `python3 tools/validate_templates.py data/templates` — ②の機械検証（1本あたり100問を実生成）
- `python3 tools/preview_templates.py [単元ID] --samples 2` — ④の人の検品用に、問題例・正解・解説を出力

②の機械検証で確認していること:

- スキーマ・式の妥当性、制約の充足可能性、プレースホルダの解決
- **すべての変数・派生値・解答が整数になること**（Postgres の整数除算と Python の除算の結果が
  食い違うのを防ぐため。整数に限れば両者は必ず一致する）
- choice形式の選択肢の重複・正解との衝突

さらに、第1弾では次の実機検証も行った（2026-08-27）:

- ローカルPostgreSQLに全103本を投入し、**各テンプレートを20回ずつ実生成**して
  エラー・未解決プレースホルダがないことを確認（103本OK / NG 0本）
- **Python検証器とPostgres実装のクロス検証**（同じ変数から同じ派生値・解答が得られるか）を
  325件比較し、不一致0件

- MVP期間（被験者2名）は ④ を**運営者のスポットチェック**とし、eスピ！展開（正式ローンチ）までに全テンプレートの人力チェックを完了させる。
- 検品で不合格になったテンプレートは draft に差し戻し、修正理由を記録する。
- 生成部隊（今後確保）はこのフローの ①〜③ を担い、④ の体制はローンチ前に整える。

## 5. テンプレートの配置

```
data/templates/
├── samples/          # 最初に試作した4本（形式の参考例）
└── math/<単元ID>/    # 第1弾の本番テンプレート（99本）
```

ファイル名はテンプレートID（`T-<単元ID>-<連番>.yaml`）。**リポジトリのYAMLが正**で、
`python3 tools/gen_seed_sql.py > supabase/seed.sql` でDB投入用SQLを生成する。

形式の例として、ケース分岐型 choice（証明の穴埋めなどパターンが有限な問題）は
`case_var` を使って記述する（`data/templates/samples/T-M2-B2-001.yaml` 参照）。
